# 2026.242.1719 — fix(chrome-sway): advance stale pins so the candy gate is green again

## Summary

`charly box validate` fails on `main` — this repo's own CI gate is red:

```
$ charly box validate
charly: error: command "validate": 3 validation errors:
                 candy "github.com/opencharly/pod-chrome-cdp" depends: unknown candy "plugin-cdp"
                 candy "github.com/opencharly/pod-dbus" depends: unknown candy "supervisord"
                 candy "github.com/opencharly/pod-chrome-cdp" candy: unknown candy "chrome-devtools-mcp"
exit 1
```

**Root cause, not the symptom.** The pinned versions predate the move from BARE dependency
names to full `@github` refs. `pod-chrome-cdp@v2026.235.2110` declares its dependencies as
bare `plugin-cdp` and `chrome-devtools-mcp`, which resolve to nothing outside a project that
happens to define those names. `v2026.240.1559` declares the same dependencies properly:

```yaml
- '@github.com/opencharly/plugin-cdp/candy/plugin-cdp:v2026.237.1416'
- '@github.com/opencharly/pod-chrome-devtools-mcp:v2026.239.1557'
```

The `pod-dbus` → `supervisord` error is the same class one level further down, and clears
with `pod-sway`, whose newer release pins `pod-dbus` properly rather than by bare name.

So two pins move and all three errors go. No packages, services or plan steps change.

### How it was found

Removing a version-skew warning in a downstream consumer
(opencharly/layer-sway-desktop#3). That repin could not land because *its* gate was red, and
tracing why led here. Rather than label either repo's red main "pre-existing", the cause is
fixed at the root.

## How tested

Before, on unmodified `main`:

```
$ git checkout main && charly box validate
3 validation errors
exit 1
```

After, on this branch:

```
$ charly box validate
exit 0
```

Run with charly **`v2026.238.1242`** — the version this repo's `deploy.yml` clones and
builds — so it is the same gate CI runs, not a newer local binary. (A newer charly rejects
this repo's `2026.232.0520` schema stamp outright, which is exactly why matching the binary
to the pin matters.)

Both exit codes were read directly from `charly box validate`, not through a pipeline —
worth stating because I previously misreported an `rc=0` here that was really `grep`'s exit
status rather than charly's.
